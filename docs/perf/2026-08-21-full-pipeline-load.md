# 최종 파이프라인 부하 테스트 — 대기열→HELD→결제 (k6, 로컬 vs 배포 VM)

**작성:** 2026-08-21 · **관련:** ADR 0017(대기열), ADR 0018(모의 결제), ADR 0019/0020(배포·관측)

W2 문서(`2026-07-16-w2-lock-comparison.md`)는 재고 차감 5전략만 비교했다. 그 이후
대기열(ADR 0017)·모의 결제(ADR 0018)가 붙어 지금 실제 사용자가 겪는 흐름은
**게이트 → 대기열 입장 → 입장 허가 대기 → HELD 예매 → 결제 접수**로 훨씬 길어졌다.
이 문서는 그 전체 파이프라인을 처음으로 k6로 측정한다.

## 측정 방법

| 항목 | 값 |
|---|---|
| 도구 | k6 v2.2.0 |
| 스크립트 | `apps/api/test/load/full_pipeline_load.js`, `full_pipeline_bench.sh` (W2 스크립트와 별도 — 대상 흐름 자체가 다름) |
| 시나리오 | VU마다 서로 다른 실제 유저 계정으로 "① 대기열 입장 → ② 입장 허가까지 폴링 → ③ HELD 예매 → ④ 결제 접수"를 1회 수행(`iterations = VUS`, 동시 도전 재현) |
| 입장 허가 설정 | `ADMISSION_BATCH_SIZE=20`, `ADMISSION_INTERVAL_MS=2000`(2초마다 20명씩) — 두 환경 동일 |
| 결제 판정 | 80%/20% 확률 성공/실패(ADR 0018) — k6는 "결제 접수(202)"까지만 측정, 최종 확정/취소는 비동기라 별도 확인 |

두 환경을 같이 쟀다 — **절대 수치를 그대로 비교하면 안 되는 이유**는 해석 참고.

| | 로컬 | 배포 VM |
|---|---|---|
| 서버 | 로컬 `pnpm start:dev` | AWS EC2 t3.micro(RAM 1GB, 컨테이너 6개 상주) |
| DB | 로컬 Postgres(docker-compose) | Neon(클라우드, 별도 네트워크 홉) |
| 클라이언트 위치 | 서버와 같은 머신 | 로컬 컴퓨터 → 인터넷 → AWS 서울 |
| VUS / STOCK | 150 / 100 | 8 / 20 (VM 자원 보호 위해 소규모만) |

## 결과

| 지표 | 로컬 (150 VU) | 배포 VM (8 VU) |
|---|---|---|
| 입장 허가(admitted) | 126 | 8 |
| 재고 소진(sold_out) | 24 | 0 |
| 허가 타임아웃 | 0 | 0 |
| 결제 접수(payment_started) | 126 | 8 |
| admit_wait avg / p95 / max | 6,447ms / 10,695ms / 12,676ms | 2,343ms / 2,778ms / 2,801ms |
| journey(입장~결제접수) avg / p95 / max | 7,614ms / 14,726ms / 14,739ms | 3,154ms / 3,709ms / 3,758ms |
| **개별 HTTP 요청** avg / p95 / p99 | **51.8ms / 110.4ms / 137.6ms** | **329.8ms / 843.8ms / 967.2ms** |
| 체크 성공률 | 100%(276/276) | 100%(16/16) |

> `http_req_failed`(로컬 60.6%, VM 23.2%)는 실제 실패가 아니다 — 입장 허가를 기다리며
> 의도적으로 보낸 예매 시도가 403(아직 대기중)을 받는 것을 k6가 "실패"로 집계할 뿐이고,
> `checks`(대기열 입장 202·결제 접수 202)는 두 환경 다 100%였다.

## 해석

- **`admit_wait`는 대기열 정책 자체가 만드는 지연**이지 병목이 아니다. 로컬 150명은
  20명/2초 배치로 8라운드(≈16초) 걸려야 전원 처리되는 게 설계상 정상이고, 실측
  p99(12.7초)도 그 산수와 일치한다. VM 8명은 첫 배치(20명 한도) 안에 다 들어가
  2~3초 만에 끝났다 — **인원이 배치 크기보다 적으면 대기열 지연 자체가 거의 없다.**
- **로컬↔VM 개별 요청 지연 차이(약 6~8배)는 예상된 것이고, 원인은 이미 알고 있다**:
  ① VM은 Neon(클라우드 DB)을 쓰는데 이건 로컬 Postgres와 달리 네트워크를 한 번
  더 거친다(ADR 0010이 W2 부하테스트를 로컬 DB로 분리해둔 이유와 동일). ② 클라이언트가
  로컬 실행 시 서버와 물리적으로 같은 머신이라 왕복 시간이 0에 가깝지만, VM 실행
  시엔 실제 인터넷 왕복이 낀다. ③ t3.micro는 버스터블 인스턴스라 로컬 개발 머신보다
  원천적으로 약하다. **이 문서의 목적은 "VM이 로컬보다 느리다"를 확인하는 게 아니라,
  그 격차의 크기를 숫자로 남겨 다음에 실제 지연 이슈가 생겼을 때 "이게 원래 격차 범위
  안인지 아닌지"를 판단할 기준선을 두는 것.**
- **재고 소진(sold_out)이 정확히 24건** — STOCK 100에 최대 150명이 도전했으니 최소
  50명은 재고 부족을 겪어야 정상인데 24건만 나온 건, 입장 허가 자체가 20명/배치라
  뒤 배치(6~8라운드)로 갈수록 도전자가 줄어들며 재고도 그만큼만 깎였기 때문 —
  **대기열이 "한꺼번에 재고를 다 털어가는 상황"을 완화하는 효과가 이 실측에서도
  드러난다**(ADR 0017이 예상한 부수 효과와 일치).
- **관측 파이프라인(오늘 만든 것) 검증 겸용**: VM 테스트 직후 Prometheus에 직접
  `sum(rate(http_requests_total[2m]))` 질의해 이 부하가 실제로 잡혔음을 확인했다 —
  이번 실측은 동시에 "Grafana/Prometheus가 실전 트래픽을 놓치지 않는지"의 첫 실사용 검증이기도 하다.

## 결론

- 대기열 정책(20명/2초)은 설계한 산수 그대로 동작한다 — `admit_wait`은 버그가 아니라
  **의도된 속도 제한**(ADR 0017 "다운스트림 보호" 목적)이다.
- 개별 요청 자체는 로컬·VM 모두 초 단위가 아니라 밀리초~1초 이내로 응답한다 — VM이
  로컬보다 느린 건 사실이지만, **사용자가 못 견딜 정도의 지연은 아니다**(VM p99도 1초 미만).
- 로컬↔VM 격차(6~8배)의 원인은 전부 설명 가능한 요인(DB 위치·네트워크 왕복·인스턴스
  사양)으로 소급된다 — 원인 불명의 이상 지연은 없었다.
- t3.micro(RAM 1GB)에 컨테이너 6개(redis/api/web/node-exporter/prometheus/grafana)가
  이미 상주한 상태에서도 소규모 부하(8 VU)로는 메모리·컨테이너 상태에 이상이 없었다
  (테스트 직후 `docker compose ps` 전부 `Up`, 스왑 사용량도 안정 범위).
