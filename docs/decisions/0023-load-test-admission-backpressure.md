# 0023. 대용량 테스트 입장 허가에 백프레셔 도입 — 처리량을 넘는 인원은 들이지 않는다

- 상태: Accepted
- 날짜: 2026-09-01
- 관련: 0014(예매 전략), 0015(정합성 설계), 0016(공개 데모 모드), 0017(입장 대기열)

## 맥락 (Context)

배포 VM에서 재고 10,000·VU 5,000 규모로 대용량 트래픽 테스트를 실사용하며 세 가지 문제가 연쇄적으로 발견됐다.

1. **DB 커넥션 풀 고갈**: Prisma `connection_limit`이 VM의 vCPU 기반 자동 계산값(3)으로 잡혀 있어, 100명씩 동시에 쏘는 투입 설계와 충돌해 대부분이 10초 풀 타임아웃으로 실패했다. → `connection_limit=20`(Neon pooled 엔드포인트 실측 기반)으로 수정.
2. **BullMQ 워커 concurrency 기본값**: `payment`/`confirm` 큐 워커가 `@Processor(QUEUE_NAME)`을 옵션 없이 등록해 BullMQ 기본값(1)을 그대로 물려받고 있었다 — job을 한 번에 하나씩만 처리해, 5,000명이 몰리면 결제 job 하나가 처리되기까지 실측 3분 34초가 걸렸다. → `{ concurrency: 20 }`으로 상향(DB 커넥션 풀 크기와 맞춤).
3. **위 두 수정 후에도 남는 근본 문제**: `HELD` TTL(30초)은 벽시계 기준으로 고정인데, 입장 허가(`LoadTestAdmissionProcessor`)는 **대기열에 남은 인원 비율만 보고**(포아송 근사, 남은 인원의 20%·최소 50·최대 1,000/초) 결제 파이프라인의 실제 처리 능력과 무관하게 최대 1,000명/초까지 사람을 들여보낸다. 3,000명 규모로 재현해보니 concurrency=20을 적용해도 `Payment→PAID`인데 `Reservation`은 `EXPIRED`로 남는 정합성 불일치가 1,199건 발생했다 — **1·2번을 아무리 개선해도, 입장 허가 속도가 그 처리량을 고려하지 않는 한 VU 규모를 키우면 언제든 재현되는 구조적 문제**였다(사용자가 이 지점을 직접 짚었다: "물리적으로 성능을 높이는 것만이 답인가").

## 결정 (Decision)

**Little's Law(`L = λ·W`)를 적용해, 입장 허가가 대기열 크기뿐 아니라 "지금 이미 결제 처리 중인 인원 수"도 함께 보고 스스로 속도를 늦추게 한다.**

- `L`(동시에 시스템 안에 있는 인원) = 현재 `HELD` 상태 예매 수(`reservation.count`)
- `λ`(처리량) = 결제→확정 파이프라인의 실측 초당 처리 건수, env `LOAD_TEST_PAYMENT_THROUGHPUT_PER_SEC`(기본 60 — 아래 실측 근거)
- `W` = 입장 허가창, 기존 `LOAD_TEST_ADMISSION_WINDOW_MS`(30초)
- 매 틱: `허가 가능 인원 = min(포아송이 원래 뽑은 배치 크기, max(0, λ×W − 현재 L))`

뒷단이 밀리면(`L`이 상한에 가까워지면) 이번 틱엔 아무도 새로 들이지 않고, 대기열(TTL 없음)에서 계속 기다리게 한다 — 아무도 "허가는 됐는데 조용히 사라지는" 일이 없다.

**처리량 실측**: 5,000명을 투입해 결제 큐를 포화시킨 뒤 `Payment.updatedAt` 분포를 1초 단위로 집계 — 가상 유저 생성이 끝나고 결제/확정 큐만 순수하게 밀린 백로그를 처리하는 구간(약 40초 지속)에서 **평균 초당 70.8건**(47~90 범위) 처리됨을 확인. 실제로는 가상 유저 생성 트래픽과도 경합하므로 여유를 두고 **60**을 기본값으로 잡는다.

**보완 — 정합성 방어선**: 백프레셔가 경합 "빈도"를 줄이지만 완전히 없앨 순 없다(허가 직후 예매 시도까지의 랜덤 지연 등으로 `L` 측정에 약간의 지연이 있음, Little's Law 자체가 평균적 관계). `payment.processor.ts`의 성공 경로에도 실패 경로와 대칭으로 `updateMany(WHERE status=HELD)` 가드를 추가해, sweep이 먼저 회수한 예매는 결제가 아무리 늦게 처리돼도 `PAID`로 남지 않고 `FAILED`로 정직하게 처리되도록 했다. **역할 분담**: 백프레셔는 "얼마나 자주 겪는지"를 줄이고, 이 가드는 "겪었을 때 거짓 데이터가 안 남게" 보장한다 — 하나가 다른 하나를 대체하지 않는다.

## 고려한 대안 (Alternatives)

| 주제 | 대안 | 채택하지 않은 이유 |
|---|---|---|
| 문제 대응 방향 | HELD TTL 연장 / sweep·만료 시에도 SSE 방송 / 프론트 타임아웃 | 셋 다 "밀린 뒤 어떻게 버틸까"에 대한 완화책이지 "왜 밀리는가"의 근본 해결이 아니다. VU 규모를 계속 키우면 TTL을 아무리 늘려도 다시 재현된다(사용자 지적, 채택된 결정으로 대체). 다만 이 셋은 백프레셔로도 못 막는 극단적 잔여 상황의 안전망으로는 여전히 유효해, 별도로 필요해지면 다시 검토한다. |
| 처리량 상한 자체를 계속 높인다(커넥션·concurrency 무한정 증설) | 재고 카운터(단일 행 경합, ADR 0014)와 달리 예매·결제 쓰기는 사용자마다 다른 행이라 커넥션을 늘리면 이론상 계속 오르지만, Neon 실측 상한(~87 슬롯)·비용·이 프로젝트가 무료 티어 학습용이라는 점(ADR 0010) 때문에 무한정 투자할 이유가 없다. 처리량을 "주어진 값"으로 받아들이고 허가 속도를 거기 맞추는 게 이 프로젝트 맥락에 맞다. |
| 처리량(λ) 측정 방식 | 실시간 적응형 측정(최근 N초의 확정 속도를 롤링 집계) | 더 정확하고 인프라를 바꿔도 자동으로 재보정되지만, 구현 복잡도가 한 단계 더 높다(콜드 스타트 시 기준값 부재, 노이즈 처리 등). 이번엔 실측 기반 정적 설정값(다른 `LOAD_TEST_SIM_BATCH_*` 상수와 같은 방식)으로 시작하고, 필요해지면 적응형으로 발전시키는 걸 백로그로 남긴다. |
| `L`(동시 처리 중 인원) 측정 방식 | Redis `admitted:event:{id}:*` 키 개수를 SCAN | 허가된 순간부터 카운트할 수 있어 더 즉각적이지만, 키가 많아지면 SCAN 자체가 부담이고 이 코드베이스는 이미 `heldCount` 등을 `reservation.count`/`groupBy`로 재는 관례가 있다. HELD 카운트 쪽이 구현이 단순하고 기존 패턴과 일관적이라 채택 — 허가 직후 잠깐의 지연은 감수한다. |

## 근거 (Rationale)

- **선착순 티켓팅의 핵심 교훈과 정확히 맞닿아 있다.** 입장 대기열(ADR 0017)의 원래 목적이 "관문에 도전할 자격을 조절"하는 것인데, 지금까지는 그 조절 기준이 대기열 크기뿐이었다 — 정작 관문 뒤(결제 파이프라인)의 실제 처리 능력은 전혀 보지 않았다. 백프레셔는 이 설계의 원래 의도를 완성하는 것이지 새 개념을 얹는 게 아니다.
- **"느리지만 정직한" 쪽을 택한다.** VU를 더 키우면 전체 처리 시간이 비례해 늘어난다(예: 1만 명 처리에 10분이었다면 10만 명은 100분) — 이건 결함이 아니라 자기 용량을 존중하는 시스템의 정직한 동작이다. 반대(다 들여보내고 일부가 조용히 깨지는 것)가 이번에 실제로 겪은 문제였고, 실제 대형 티켓팅 서비스의 가상 대기실도 같은 이유로 이렇게 동작한다.
- **재고 차감(Redis, 0014)과 예매·결제 쓰기(Postgres)는 성격이 다른 병목이다.** 전자는 모두가 같은 행을 두고 경합해 이미 구조적 한계에 가깝고, 후자는 사용자마다 다른 행이라 인프라 투자로 계속 개선 가능하다 — 이 구분을 명확히 해야 "어디에 돈과 시간을 더 쓸 가치가 있는지" 판단할 수 있다.
- **정합성 가드(HELD 재확인)는 백프레셔와 다른 층위의 방어다.** 확률적으로 줄어든 잔여 경합이라도, "결제 성공"이라는 거짓 데이터가 조금이라도 남는 건 실제 서비스라면 심각한 문제라 — 빈도를 줄이는 것과 별개로 반드시 막아야 했다.

## 결과 (Consequences)

**이득**
- VU 규모를 키워도(향후 상한 상향 시) 정합성이 깨지지 않는다 — "테스트가 오래 걸릴 뿐" 상태로 안전하게 스케일된다.
- "결제는 성공, 티켓은 없음" 같은 거짓 데이터가 구조적으로 방지된다.
- 처리량 실측·백프레셔 계산이 기존 관례(env 설정값, `reservation.count` 패턴)를 그대로 따라 코드 복잡도가 크게 늘지 않는다.

**감수할 것**
- 처리량(λ)이 정적 설정값이라, 인프라(커넥션 풀·concurrency)를 바꾸면 재실측해 값을 갱신해야 한다(자동 재보정 아님).
- `L` 측정(HELD 카운트)이 허가 직후 잠깐의 지연을 갖는다 — Little's Law는 평균적 관계라 순간값의 엄밀한 보장은 아니다.
- 뒷단이 밀리면 대기열에서 기다리는 시간이 늘어난다 — 이건 의도된 트레이드오프지만, 사용자 체감상 "생각보다 오래 기다린다"는 인상을 줄 수 있다(안내 문구 등 UX 보완은 이후 필요시 별도 검토).

**후속 작업(백로그)**
- VU/재고 상한(현재 10,000) 상향은 이 ADR의 전제 조건(백프레셔)이 갖춰졌으므로 이제 안전하지만, 이번 범위에서는 진행하지 않고 별도로 판단한다.
- 처리량(λ) 적응형 측정으로 전환.
- TTL 연장·만료 시 SSE 방송·프론트 타임아웃 — 백프레셔로도 못 막는 극단적 잔여 상황의 안전망으로 필요해지면 재검토.
