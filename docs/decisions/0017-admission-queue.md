# 0017. 선착순 입장 대기열 — Redis Sorted Set 기반 admission 제어

- 상태: Accepted
- 날짜: 2026-08-06
- 관련: 0004(Redis), 0005(BullMQ), 0006(SSE), 0014(예매 전략), 0015(정합성 설계), 0016(공개 데모 모드)

## 맥락 (Context)

원래 기획안(`02_서비스_기획안.md`)의 핵심 시나리오는 "60석에 300명 동시 접속. 유저는 **대기열에서 실시간 순번을 보며 기다리고**, 입장하면 좌석을 잡는다"였다. 그런데 ADR 0014/0015를 구현하며 "대기열(순번 기다리기)" 대신 **즉시 판정 관문**(Redis `DECRBY` — 되면 HELD, 안 되면 즉시 409)으로 방향을 틀었다. 이건 근거가 확실한 더 나은 엔지니어링 선택이었지만(k6로 증명, 0014), 그 과정에서 기획안이 그리던 "내 차례가 언제인지" 경험이 **조용히 함께 빠졌다** — 어떤 ADR도 이걸 명시적으로 드롭한다고 남기지 않았다.

방문자(개발자 본인)가 실제로 완성된 데모를 써보며 이 gap을 발견했다: 지금 아키텍처엔 "차례"라는 개념 자체가 없다. 이 프로젝트의 실제 사용자는 소수(개발자 본인 + 공유 비번을 받은 사람)뿐이라, 대기열의 목적은 **진짜 대규모 트래픽 방어가 아니라 원래 기획의 학습 포인트(입장 제어/pacing)를 완결하고 포트폴리오 서사를 넓히는 것**이다. 대규모 동시성은 서버측 시뮬레이션(0016)으로 인위적으로 재현해 검증한다.

## 결정 (Decision)

**관문(0014)과 대기열을 별도 계층으로 분리해 조합한다.** 대기열은 "언제 관문에 도전할 자격을 주는가"만 관장하고, 관문·HELD 선기록·확정 큐·SSE(0014/0015) 파이프라인은 전혀 손대지 않는다.

```
[대기열 진입] → (입장 처리 워커가 주기적으로 N명씩 허가) → [입장 허가(TTL 8초, env QUEUE_ADMISSION_WINDOW_MS)]
                                                                  │
                                                     허가 안에서만 아래 파이프라인 진입 가능
                                                                  ▼
                                          [관문 DECRBY] → [HELD] → [큐] → [확정] → [SSE]   ← 0014/0015, 무변경
```

1. **대기열 자료구조**: Redis Sorted Set `queue:event:{id}` — member=userId, score=진입 시각. FIFO 순서를 자연스럽게 보장(관문의 `DECRBY`보다도 가벼운 연산).
2. **입장(admission) 처리**: BullMQ repeatable job이 짧은 주기(예: 2초)마다 대기열 앞에서 N명을 `ZPOPMIN`으로 꺼내, 각자에게 `admitted:event:{id}:{userId}` 키를 **TTL 8초(기본값)**로 세팅한다 — "입장 허가창".
3. **허가 검증**: `queue.service.ts`의 `assertAdmitted(eventId, userId)` 한 곳이 이 키의 존재를 확인한다. **실제 사용자(컨트롤러 경로)와 가상 유저(데모 서비스 경로) 둘 다 이 메서드를 반드시 통과**해야 예매(관문 도전)를 시도할 수 있다. W2 5전략 벤치마크(`?strategy=naive/pessimistic/optimistic/atomic`)는 대기열과 무관하므로 이 체크 대상이 아니다 — `strategy=held` 경로에만 적용한다.
4. **순번 확인**: 대기 중인 사용자에게 `ZRANK` 기반 순번을 SSE로 실시간 push(0016의 stats 스트림과 같은 1초 폴링 패턴 재사용).
5. **허가창 만료 처리**: Redis 키의 TTL이 자연 만료되게 둔다 — 별도 회수(sweep) 잡을 만들지 않는다. HELD(0015)는 재고를 실제로 붙잡고 있어 DB에 흔적을 남겨 재구성해야 했지만, 입장 허가는 **아직 재고를 전혀 건드리지 않은 상태**라 유실돼도 정합성 문제가 없다.
6. **가상 유저(시뮬레이션)의 현실성**: 입장 허가를 받아도 **20% 확률로 아예 시도하지 않고**(포기), 나머지 80%는 **0.5~10초 사이 랜덤 지연** 후 시도한다 — 지연 범위를 허가창(8초)보다 살짝 넓게 잡아 대부분은 창 안에 들어오되 느린 일부만 창을 넘기면 실제 사용자처럼 "허가 만료"로 자연스럽게 실패한다. 즉 가상 유저도 3번의 `assertAdmitted`를 그대로 통과해야 하며, 이들을 위한 특수 코드 경로는 만들지 않는다.

## 고려한 대안 (Alternatives)

| 주제 | 대안 | 채택하지 않은 이유 |
|---|---|---|
| 입장 처리 리듬 | 재고 소진 속도에 맞춰 N을 동적으로 조절 | 더 정교하지만 이 프로젝트 스케일(시뮬 최대 300 VU)엔 과설계. 0016의 시뮬 배치 패턴(20명×300ms)으로 이미 "계단식 재현" 학습 포인트를 보여주고 있어, 대기열에도 같은 수준의 단순한 고정 배치면 충분. |
| 허가창 회수 | DB에 "허가" 상태를 기록하고 sweep 잡(0015의 HELD TTL 회수처럼)으로 정리 | 회수 대상(입장 허가)이 재고를 붙잡고 있지 않아, DB 흔적·재구성 로직을 늘릴 이유가 없다. Redis TTL 자연 만료로 충분 — 불필요한 복잡도. |
| 가상 유저 행동 | 입장 허가와 동시에 즉시 자동 예매(지연·포기 없음) | 이러면 "허가창 만료" 경로가 실제 사용자 전용이 되어 시뮬레이션으로 검증되지 않는다. 랜덤 지연+포기를 넣으면 가상 유저도 같은 코드 경로를 타 자연스럽게 검증되고, 데모도 더 현실적으로 보인다. |
| 순번 통보 | 클라이언트 폴링 | 0006에서 이미 폴링을 기각한 근거(요청 폭탄, 실시간성 저하)가 그대로 적용됨. 대기열은 오히려 폴링과 더 안 맞는다(대량 동시 대기자가 동시에 폴링하면 그 자체가 부하). → SSE 재사용. |

## 근거 (Rationale)

- **관문과 대기열은 경쟁 관계가 아니라 계층 관계다.** 대기열은 "언제 관문에 도전하게 해주는가"만 조절할 뿐, 초과판매 방지라는 관문의 역할(0014)을 대체하지 않는다. 대기열을 얹어도 관문 코드는 한 글자도 안 바뀐다 — 이게 이 설계가 "수술적"인 이유다.
- **대기열의 진짜 존재 이유를 솔직하게 인정한다.** 이 프로젝트의 실사용자는 소수(개발자 본인 + 공유 대상)뿐이라, 대기열이 실제로 "방어"할 트래픽은 없다. 존재 이유는 ① 원래 기획(PRD)이 그리던 "내 차례" 학습 포인트를 완결하고 ② 포트폴리오에 "입장 제어(admission control)" 챕터를 추가하는 것이다. 이걸 숨기지 않고 명시하는 게 이 ADR의 목적이다.
- **가상 유저에게 실사용자와 동일한 `assertAdmitted` 체크를 강제한 것**은 "테스트되는 코드 경로를 하나로 통합한다"는 판단이다. 특수 케이스가 없어 유지보수 부담이 줄고, 시뮬레이션 자체가 이 기능의 최선의 자동 검증 도구를 겸한다.
- **Redis TTL 자연 만료**는 0015가 HELD를 DB에 남긴 이유(Redis 유실 시에도 재구성 가능해야 함)와 대비된다. 입장 허가는 재고를 잡고 있지 않아 유실돼도 정합성이 깨지지 않으므로, 굳이 DB화해 재구성 로직을 늘리는 건 불필요한 복잡도다(CLAUDE.md §0 "불필요한 복잡도에는 반론을 제기할 것").

## 결과 (Consequences)

**이득**
- 원래 기획(PRD)의 "실시간 순번" 학습 포인트가 완결된다.
- 포트폴리오 서사가 "동시성 처리"에서 "입장 제어(admission control)"까지 확장된다.
- 관문·HELD·확정·SSE(0014/0015) 기존 코드는 전혀 안 바뀐다 — 새 계층 하나만 추가.

**감수할 것**
- 새 모듈(`queue`) 추가로 복잡도가 늘어난다.
- 실제 대규모 트래픽에서의 효과는 검증되지 않는다(시뮬레이션으로만 검증 — 위 근거에서 이미 인정한 트레이드오프).
- 가상 유저 로직이 확률 기반(20% 포기, 0.5~10초 랜덤 지연)이라 매 실행 결과가 달라진다 — 데모 목적상 허용하지만, W2 k6 벤치마크처럼 "재현 가능한 수치 비교"의 대상은 아니다.

**후속 작업(구현 시)**
- `apps/api/src/queue/` 신규 모듈(서비스·컨트롤러·워커·상수).
- `reservations.controller.ts`에 `strategy=held`일 때만 `assertAdmitted` 체크 연결.
- `demo.service.ts`의 가상 유저 주입 로직을 "대기열 경유"로 수정(포기·랜덤 지연 포함).
- 프론트: 대기열 상태 섹션(순번 SSE, 입장 허가 시 기존 `BookingForm` 노출).
- 세부는 구현 중 조정될 수 있으며, 크게 바뀌면 후속 ADR로 남긴다.
