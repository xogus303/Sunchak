# 0018. 모의 결제 — 확정 트리거를 HELD 생성에서 결제 성공으로 이동

- 상태: Accepted
- 날짜: 2026-08-06
- 관련: 0005(BullMQ), 0006(SSE), 0009(스키마), 0014(예매 전략), 0015(정합성 설계), 0017(대기열)

> **오타 정정 (2026-08-08 — 배포 전 ADR 점검 중 발견)**: 아래 본문이 비교 근거로 인용하는 "HELD TTL 5분"은 PRD 원안의 숫자다 — 실제 `HELD_TTL_MS`는 이 ADR과 같은 날 있었던 다른 작업에서 **30초**로 조정됐다(`apps/api/src/reservations/reservations.service.ts`, DEVLOG "결제 TTL 30초" 항목 참고). 방향성 있는 비교(어떤 TTL이든 "기다리기" vs "즉시 반환")는 그대로 유효하니 본문은 안 고치고, 실제 숫자를 헷갈리지 않도록 여기 정정만 남긴다.

## 맥락 (Context)

PRD(`02_서비스_기획안.md`)는 예매 흐름을 "좌석 홀드(5분 타이머) → **모의 결제** → 성공 시 확정 / 실패·타임아웃 시 좌석 반환"으로 그렸고, 화면 정의(§6)에도 "모의 결제 버튼, 상태 폴링 — 비동기 상태(pending→done)"이 명시돼 있다. `Payment` 테이블도 이 흐름을 전제로 W1 ERD에서 이미 만들어졌다(`status: PENDING/PAID/FAILED`).

그런데 ADR 0015 구현 시점에 결제 자체는 만들지 않고 워커가 HELD를 곧바로 CONFIRMED로 뒤집게 해뒀다 — ADR 0015 본문에 이미 "이건 결제 stub이고, 실제론 결제 완료(PG 웹훅)가 confirm job을 태워야 한다"고 명시적으로 적어뒀다. 즉 이 자리는 애초부터 "나중에 결제가 끼어들 seam"으로 설계돼 있었다.

## 결정 (Decision)

**확정(confirm) job을 투입하는 시점을 "HELD 생성"에서 "결제 성공"으로 옮긴다.** 관문·HELD·기존 확정 워커(`ConfirmProcessor`)·SSE 스트림은 전혀 손대지 않는다 — 그 앞에 결제 단계 하나를 끼워 넣을 뿐이다.

```
[예매하기] → HELD (Payment 행 생성, status=PENDING, confirm job은 아직 안 넣음)
     │
[결제하기 클릭] → POST /reservations/:id/pay → 'payment' 큐에 job 투입 → 즉시 202(PENDING)
     │
[PaymentProcessor] → 80% 성공 / 20% 실패(모의, 랜덤)
     ├─ 성공 → Payment: PAID → 기존 'confirm' 큐에 job 투입(ConfirmProcessor 무변경 재사용) → HELD→CONFIRMED
     └─ 실패 → Payment: FAILED → Reservation: CANCELLED, Redis 재고 즉시 INCRBY 반환(사용자 확인 후 채택 — TTL 만료 대기 대신 즉시 반환), ReservationEventsService로 CANCELLED 방송
     │
[SSE] 기존 `/reservations/:id/stream` 무변경 — "HELD가 아니면 종료 상태"로 이미 일반화돼 있어 CONFIRMED든 CANCELLED든 그대로 흘려보낸다.
```

- **결제도 비동기(큐)**: PRD가 "비동기 상태(pending→done)"를 명시했고, 이 프로젝트의 학습 목표(큐·비동기)와도 맞아 confirm과 같은 BullMQ 패턴(`payment` 큐, `PaymentProcessor`)을 그대로 재사용한다.
- **`Payment.idempotencyKey` 재검토 결론(STATUS.md 백로그 항목 해소)**: Reservation의 `idempotencyKey`는 `[userId, idempotencyKey]` 복합 unique로 스코프를 좁혀야 했던 반면(같은 유저의 "재전송"과 "새 주문"을 구분해야 함 — 여러 Reservation 행이 한 유저에 속하므로), Payment는 **`reservationId`가 이미 `@unique`(1:1)** 라 결제 재시도 자체가 그걸로 원자적으로 막힌다. 별도 복합 unique가 필요 없다 — 실제 버그 아님으로 결론.
- **실패 시 즉시 반환**(vs HELD TTL 5분 대기): 방문자가 감으려감 없이 바로 다시 시도할 수 있고, 다른 대기자에게도 즉시 좌석이 풀린다.

## 고려한 대안 (Alternatives)

| 주제 | 대안 | 채택하지 않은 이유 |
|---|---|---|
| 결제 처리 방식 | `POST /pay`가 동기로 즉시 성공/실패 응답 | PRD가 명시한 "비동기 pending→done" UX와 안 맞고, 이 프로젝트의 큐 학습 포인트를 또 하나 놓친다. |
| 실패 시 반환 | HELD TTL(5분) 만료로 자연 반환(sweep 재사용) | 새 반환 로직 없이 기존 안전장치를 재사용하는 장점은 있지만, 사용자가 실패를 보고도 5분을 기다려야 해 UX가 나쁨(사용자 확인 후 기각). |
| 확정 트리거 | `PaymentProcessor`가 직접 Reservation을 CONFIRMED로 바꿈 | 기존 `ConfirmProcessor`(멱등 UPDATE)를 중복 구현하게 된다. 대신 성공 시 **기존 confirm 큐에 job만 투입**해 재사용 — 변경 범위 최소화. |

## 근거 (Rationale)

- **이 자리는 이미 "seam"으로 설계돼 있었다**: ADR 0015가 스스로 "결제 stub"이라 부르며 다음 단계를 예고해뒀다. 지금은 그 예고를 실행하는 것뿐 — 새 아키텍처가 아니라 미뤄둔 한 조각을 채우는 것.
- **기존 확정 경로를 재사용**하는 것이 "수술적 변경" 원칙에 맞는다. `ConfirmProcessor`는 이미 멱등하고 테스트돼 있다 — 성공 시 그 큐에 job을 넣는 것만으로 확정이 일어나게 하면 그 코드를 한 글자도 안 바꿔도 된다.
- **결제 성공률(80%)은 하드코딩**한다(env로 안 뺌) — 시뮬레이션 파라미터(0016/0017)와 달리 이건 핵심 비즈니스 로직 상수이고, 테스트에서 성공/실패 양쪽을 확인하려면 결정론적으로 만드는 게 더 나아 실제로는 테스트마다 `Math.random`을 모킹한다.

## 결과 (Consequences)

**이득**
- PRD의 결제 학습 포인트(비동기 처리, pending→done)가 완결된다.
- 기존 관문·HELD·확정·SSE 코드는 무변경.

**감수할 것**
- `reservations.service.spec.ts`의 "HELD 접수 후 자동 확정" 관련 테스트들이 더 이상 성립하지 않는다 — **의도된 동작 변경**(결제 없이 자동 확정되던 게 stub이었으므로)이라 테스트를 결제 성공 경로를 거치도록 갱신한다.
- 새 큐(`payment`) + 워커 하나가 운영 복잡도를 더한다.

**후속 작업(구현 시)**
- `createHeld()`에서 즉시 confirm job 투입 제거, 대신 `Payment` 행 생성.
- 신규 `payment.processor.ts`(같은 `reservations/` 모듈), `payments.controller.ts`(`POST /reservations/:id/pay`).
- 프론트: HELD 상태에 "결제하기" 버튼 추가, 결제 중(PENDING) 상태 표시.

## 개정 이력 (2026-09-05) — 결제·확정 큐에 우선순위 도입(가상 유저 vs 실제 유저)

**계기**: 대용량 트래픽 테스트 도중 사용자가 본인 명의로 직접 예매해보니 "결제 처리 중"에서 수십 초씩 멈췄다. 원인 조사 결과 결제(`payment`)·확정(`confirm`) 큐는 캐주얼 데모·대용량 테스트·실제 예매가 전부 공유하는데, 실제 인위적 지연은 전혀 없고(`payment.processor.ts`에 sleep 없음) 순수하게 **큐 적체**(concurrency=20, 실측 처리량 초당 약 70건 — ADR 0023)였다. 사용자 본인의 결제 job도 가상 유저 수천 명의 job과 완전히 같은 FIFO 줄에 서서 차례를 기다렸다.

사용자가 이 상황을 "입장 대기는 다른 사람을 기다릴 수 있지만, 결제까지 남의 결제를 기다리는 건 잘못된 설계"라고 지적 — 정확한 지적이다. 입장(대기열)은 "재고가 유한하고 순서가 곧 자격"이라는 서비스 본질상 대기가 필수지만, 이미 재고를 HELD로 확보한 사람의 결제 판정은 본질적으로 개인 트랜잭션이라 남과 순서를 다툴 이유가 없다(실제 PG는 트랜잭션을 독립적으로 병렬 처리한다).

처음엔 "결제 큐를 대용량 테스트 전용/실제 서비스 전용으로 물리적으로 분리"하는 방향을 검토했으나, 이 경우 사용자 본인의 클릭도 그 대용량 테스트의 참여자 중 하나이므로(같은 이벤트·같은 큐) 분리해도 체감 지연이 그대로 남는다는 걸 사용자와 논의 중 확인 — 진짜 필요한 건 "어느 큐냐"가 아니라 "같은 큐 안에서 누가 먼저 처리되냐"였다.

**결정**: `payments.service.ts`가 예약자 이메일이 `@sunchak.demo`(캐주얼 데모·대용량 테스트 가상 유저 공통 도메인)로 끝나는지로 실제/가상 유저를 판별해, 가상 유저의 job에만 BullMQ `priority` 옵션을 건다. BullMQ는 priority가 없는(0) job을 priority가 있는 job보다 항상 먼저 처리하므로(`bullmq/dist/cjs/classes/job.js` 주석), 실제 유저는 옵션을 그냥 안 주는 것만으로 가상 유저 트래픽이 아무리 쌓여도 항상 먼저 처리된다. `payment.processor.ts`도 성공 판정 시 이 값을 그대로 이어받아 `confirm` 큐 투입에도 같은 우선순위를 적용(payments.service.ts가 이미 판별한 값을 job data에 실어 넘겨, 중복 조회 없이 재사용).

**대안 비교**:
| 대안 | 채택하지 않은 이유 |
|---|---|
| 결제·확정 큐를 대용량/실제용으로 물리적 분리 | 위에서 확인했듯 "테스트 중인 본인"의 체감 지연 자체는 해결 못 함(같은 대용량 큐 안의 문제). 실제로는 다른 문제(서로 다른 컨텍스트 간 격리)에 대한 답이라 이번 범위 밖. |
| 처리량(concurrency) 자체를 더 올림 | DB 커넥션 풀(20)이 물리적 상한이라 이 프로젝트 예산에서 지속 가능하지 않음(ADR 0023과 같은 이유). |

**결과**: 실제 유저는 가상 유저 규모와 무관하게 결제·확정이 즉시(대기 없이) 처리된다. 감수할 점 — 실제 유저 요청이 끊임없이 계속 들어오면 가상 유저 job은 이론상 계속 밀릴 수 있다(starvation), 그러나 이 프로젝트에서 "실제 유저"는 사이트 소유자 본인의 산발적 테스트 클릭 수준이라 실질적 문제가 안 된다. **테스트**: `payments.service.spec.ts`/`payment.processor.spec.ts`에 각각 1건씩 추가(가상 유저 job엔 priority 옵션 포함, 실제 유저는 기존과 동일하게 옵션 없음).

### 철회 (같은 날, 2026-09-05) — "내 결제만 빠르게"가 아니라 "결제 처리 자체가 느리면 안 된다"

위 우선순위 도입 직후 사용자가 정확히 짚었다: **이 결정은 "본인 결제를 남보다 앞세우는 것"만 풀었을 뿐, "결제 시스템 처리 속도 자체가 느려선 안 된다"는 원칙은 전혀 풀지 못했다.** 가상 유저 job은 여전히 순차 처리라 느리고, 우선순위는 그 느림을 real 유저 눈에만 안 보이게 가릴 뿐이었다 — 증상 완화이지 원인 제거가 아니다.

재조사 결과 진짜 병목은 job 하나당 Neon(원격 DB) 왕복이 순차적으로 2~3번 일어나는 것(왕복 1회당 약 100ms)이었다 — concurrency=20을 곱해도 처리량이 초당 약 70건에 그치는 이유. 이 결정(우선순위)은 **철회**하고, 대신:
1. **job당 DB 왕복 자체를 줄인다**(같은 세션 후속 커밋) — "HELD 재확인/취소"와 "Payment 갱신"을 raw SQL 한 문장으로 합쳐 왕복을 절반 이하로 줄여 처리량 자체를 높인다(비용 없이 가능한 진짜 최적화).
2. **결제 단계에 도달하는 동시 인원 자체를 처리량에 맞게 제한한다**(ADR 0023 백프레셔 파라미터 조정) — `maxInFlight` 계산이 "입장 허가창(사람이 반응할 시간, 30초)"과 "결제 큐가 감당 가능한 동시 인원"이라는 서로 다른 두 개념을 같은 숫자로 섞어 쓰고 있었던 것을 분리해, 후자를 처리량 기준의 훨씬 작은 값으로 재설정한다. 이러면 결제 단계는 항상 여유 있게 유지되고, 넘치는 인원은 (원래 사용자가 원했던 대로) 입장 대기열 쪽에서 기다린다.

우선순위 코드(payments.service.ts/payment.processor.ts의 priority 분기, VIRTUAL_USER_* 상수, 관련 테스트)는 전부 되돌렸다. 이 절이 왜 왔다가 왜 철회됐는지는 학습 기록으로 남겨둔다 — 다음에 비슷한 "느림" 문제를 만나면 "누구를 먼저 처리할까"가 아니라 "왜 처리 자체가 느린가"부터 물어야 한다는 교훈.

## 개정 이력 (2026-09-09) — pay() 자체(프론트도어)의 DB 왕복도 1회로 축소

**계기**: 배포 사이트 대용량 테스트(재고 10,000·VU 5,000) 중 사용자가 "결제하기 버튼을 눌러도 반응이 늦고, '처리 중'으로 바뀐 뒤 수십 초 지나야 완료된다"고 재차 리포트. 위 2026-09-05 철회 절에서 이미 "job당 DB 왕복을 줄였다"고 기록했는데도 왜 여전히 느린지 재조사가 필요했다.

**원인**: 그 왕복 축소는 `payment.processor.ts`(큐 워커)에만 적용됐다 — `payments.service.ts`의 `pay()`(결제 요청을 접수하는 프론트도어 API 자체)는 그대로 3회 순차 Prisma 호출(소유권 확인 → 예약+이벤트 재조회 → Payment 생성)로 남아있었다. admission이 burst로 `maxInFlight`(약 1,950명)를 한꺼번에 입장시키면 그중 다수가 비슷한 타이밍에 `pay()`를 호출한다 — 격리된 800명을 동시에 `pay()`로 호출하는 실측(라이브 배경 트래픽과 무관하게 재현)으로 확인: 평소 300~450ms면 끝날 요청이 커넥션 풀(20개) 경합으로 **p50 2.8초·p90 3.9초**까지 늘어졌다. 사용자가 겪은 증상과 정확히 일치.

**결정**: `pay()`의 "확인"(소유권+HELD 상태)과 "쓰기"(Payment 생성)를 CTE 하나로 묶어 왕복을 1회로 줄인다 — `payment.processor.ts`가 이미 쓰던 패턴을 프론트도어까지 확장한 것(위 2026-09-05 결정 #1의 연장선). 에러 케이스(404/403/409) 판별은 `target`(예약+이벤트 조회, 소유권·상태 무관하게 항상 실행)과 `ins`(소유권+HELD일 때만 실행되는 Payment 생성) 두 CTE의 결과를 한 행에 같이 담아 반환해서, 애플리케이션 코드가 `targetId`(존재)·`targetUserId`(소유자)·`paymentId`(생성 성공) 세 값만으로 세 에러를 그대로 구분하게 했다.

**실측(before/after, 격리된 800명 동시 `pay()` 호출, Neon 원격 DB 기준 — 방법론은 위와 동일하게 admission·시뮬레이션 개입 없는 순수 격리 측정)**:

| 지표 | 기존(3회 왕복) | 신규(1회 왕복) | 개선 |
|---|---|---|---|
| min | 1,004ms | 193ms | 5.2배 |
| p50 | 2,844ms | 2,037ms | 28% ↓ |
| p90 | 3,943ms | 3,137ms | 20% ↓ |
| p99 | 4,171ms | 3,368ms | 19% ↓ |
| max | 4,219ms | 3,402ms | 19% ↓ |
| 800명 전체 완료 시간 | 4.24초 | 3.41초 | 20% ↓ |

**감수할 점(솔직한 평가)**: 왕복을 3→1로 줄였지만 개선 폭은 3배가 아니라 20~30%대다 — 800명이 20개 커넥션을 다투는 상황에서 대기시간 대부분은 "왕복 자체의 길이"가 아니라 "커넥션 슬롯을 기다리는 큐잉 시간"이기 때문이다(왕복이 줄면 한 사람이 슬롯을 붙잡는 시간이 짧아져 줄이 더 빨리 줄지만, 20개라는 슬롯 수 자체는 그대로다). **이건 완화책이지 근본 해결이 아니다** — 근본 해결은 처리량/커넥션 자체를 늘리거나(비용 발생) 대기 중 진행 상황을 보여주는 UX 보완(체감 개선, 실제 지연은 그대로) 중 하나가 필요하며, 둘 다 아직 미착수라 백로그로 남긴다.

**테스트**: `payments.service.spec.ts`에 404(신규, 예약 자체가 없는 케이스) 1건 추가 + 기존 4건(성공/403/409/재전송)이 새 쿼리 경로로도 그대로 통과함을 재확인. **API 148개 그린**(기존 admission 스펙 1건은 전체 스위트 동시 실행 시 간헐 실패 — 단독 실행 시 통과, 2026-09-01부터 기록된 기존 flaky 이슈로 이번 변경과 무관), tsc 클린.
