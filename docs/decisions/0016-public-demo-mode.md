# 0016. 공개 데모 모드 — 진입 게이트 + 데모 장치 + 데이터 리셋

- 상태: Accepted (2026-08-01 축 C 부분 개정, 2026-08-05 축 B-1/D·B-2 세부 확정, 2026-08-07 방문자별 격리로 §C 대안 판단 Superseded)
- 날짜: 2026-07-21
- 관련: 0006(SSE), 0010(Neon), 0011(Infisical), 0013(인증), 0014·0015(예매), 0017(입장 대기열)

> **개정 이력 (2026-08-01 — 축 C 구현 착수 시)**
> 원안은 "자동 주기 리셋 + 수동 리셋 둘 다"였다. 구현 시점에 **수동 리셋만**으로 좁혔다 — 활동 기반 idle-timeout(디바운스)까지 검토했으나 자동화 자체를 이번 범위에서 제외하기로 결정. 자동 리셋이 실제로 필요해지면(배포 후 방치 시간이 길어 매진 상태가 오래 노출되는 문제가 관측되면) 그때 재추가한다. 상세는 DEVLOG 2026-08-01 항목.

> **개정 이력 (2026-08-05 — 축 B-1/D 구현 착수 시)**
> 원안엔 없던 세부를 확정:
> - **투입 리듬**: 순수 동시 발사도, 순수 순차 투입도 아닌 **묶음(batch) 발사**로 결정. 한 번에 다 쏘면(예: 300명 동시) Redis 원자 감산이 워낙 빨라 대시보드가 숫자를 보여줄 새도 없이 1초 안에 끝나 "재현"이 안 보인다. 반대로 한 명씩 느리게 흘리면 이 프로젝트가 증명하려는 **동시 쓰기 경합 자체가 안 걸린다**(W2의 핵심 문제는 "같은 순간에 같은 재고 행을 건드릴 때"만 재현됨). 절충: **짧은 간격(예: 300ms)마다 일정 묶음(예: 10~20명)을 동시에 발사** — 묶음 안에서는 진짜 동시 요청이라 경합이 재현되고, 묶음 사이 간격 덕분에 사람이 대시보드 숫자가 계단식으로 떨어지는 걸 눈으로 따라갈 수 있다. `DEMO_SIM_MAX_VU=300` 기준 예: 20명 × 15묶음 × 300ms ≈ 4.5초.
> - **가상 유저의 신원**: `Reservation.userId`가 `User`를 참조하는 DB FK 제약이라 가짜 id는 애초에 불가능(시도할 필요 없이 확정적 실패) — **가상 유저마다 실제 `User` 레코드를 생성**한다(Google 계정처럼 `password: null`인 데모 전용 계정).
> - **가상 유저 정리**: 시뮬레이션이 만든 `User` 행은 이메일에 식별 패턴(`sim-<uuid>@sunchak.demo`)을 박아, **§C 리셋 시 `Reservation` 삭제와 함께 이 패턴의 `User`도 같이 삭제**한다(스키마 변경 없이 기존 `isDemo` 식별 취지를 이메일 패턴으로 재사용). 안 지우면 시뮬레이션마다 무료 티어 DB에 계정이 계속 쌓여 이 ADR의 근본 목적(무료 티어 보호)에 반한다.
> - **응답 형태**: 시뮬 엔드포인트는 202로 즉시 응답하고, 진행 상황은 축 B-2의 SSE stats 스트림으로 확인한다(§B.1대로).
> - **쿨다운 스코프**: **전역**(게이트 토큰으로 인증한 방문자라면 누구든 실행 가능 — per-user/IP 구분 없음). **강제 위치는 원안대로 백엔드 Redis 유지**(신뢰 경계는 API — 위 §A와 같은 논리). 프론트 버튼은 이 강제의 결과(429 여부)를 반영해 비활성화 상태를 보여줄 뿐, 버튼 비활성화 자체가 방어선은 아니다.
> - **축 B-2 푸시 방식**: W3 2.4의 SSE(이벤트 기반 — 워커가 확정하는 순간에만 `publish`)와 달리, stats는 소스가 3개(Redis 재고·DB의 HELD/CONFIRMED 합계·BullMQ 큐 적체)라 진짜 이벤트 기반으로 엮으려면 관문 DECRBY·HELD INSERT·sweep·reconcile·confirm 워커 등 **이미 완성된 W3 코드 여러 곳**을 건드려야 해서 결합도가 커진다. 대신 **폴링 기반 스냅샷**(1초 주기로 "지금 상태"를 다시 조회해 그대로 흘려보냄)으로 결정 — 기존 코드 무변경, 새 파일 하나로 완결. 대시보드 용도라 1초 지연은 체감상 무해.

> **개정 이력 (2026-08-07 — 방문자별 격리 도입, §C 대안 판단 Superseded)**
> **바뀐 것**: 데모 이벤트를 **`isDemo:true` 이벤트 1개를 모든 방문자가 공유**하던 구조에서, **로그인한 유저마다 자기 전용 데모 이벤트**를 갖는 구조로 바꿨다. `Event.demoOwnerId`(유저 FK, `@unique`)를 추가해 유저-이벤트를 1:1로 묶고, 방문할 때마다 "내 것"이 없으면 그 자리에서 만든다(`EventsService.findOrCreateOwnDemoEvent`). `EventsController.findAll`·`DemoController`의 `reset`/`simulate`/`stats/stream` 세 라우트 모두 로그인(JWT) 가드를 추가해 "누구의" 이벤트인지 식별한다.
>
> **계기**: 사용자가 회사·집 두 기기(§9)에서 **동시에** 데모를 테스트하면서, 한쪽에서 가상 유저를 투입하거나 리셋을 누르면 다른 쪽이 테스트 중이던 재고·대기열·대시보드 숫자까지 같이 흔들리는 문제를 실측으로 발견했다. 이 프로젝트 자체가 "두 기기 재현성"(§9)을 요구조건으로 이미 깔고 있었는데, 데모 상태가 기기(엄밀히는 로그인 유저)별로 분리돼 있지 않았던 게 그 요구와 충돌한 셈이다.
>
> **원안(§C 대안 표)이 틀렸던 지점**: 이 ADR 최초 버전은 "방문자별 격리 이벤트는 세션별 데이터 분리 설계라 복잡도 과함(단일 사용처에 오버엔지니어링)"이라 판단해 기각했다. 그 판단은 **모든 Redis 키가 처음부터 `eventId`로 네임스페이스돼 있었다**(`stock:event:{id}`, `queue:event:{id}`, `soldout:event:{id}`, `abandoned:event:{id}`, `admitted:event:{id}:{userId}`)는 사실을 충분히 고려하지 못했다 — "유저마다 격리"는 실제로는 "유저마다 새 Redis 네임스페이스"가 아니라 "유저마다 새 `eventId` 하나"만 있으면 끝나는 문제였다. 즉 다운스트림(Redis·큐·예매)은 이미 준비돼 있었고, 손대야 할 지점은 "이 요청이 어느 이벤트를 가리키는가"를 결정하는 최상단 한 곳(`EventsService`)뿐이었다 — 원안이 예상한 "세션별 데이터 분리 설계"만큼의 복잡도가 아니었다.
>
> **부수 효과로 발견한 버그**: 이 작업 중 실측으로 새 버그를 하나 발견해 같이 고쳤다 — `ReservationsService.createHeld`(held 예매 전략)는 DB가 아니라 Redis `stock:event:{id}` 키를 `DECRBY`해서 재고를 차감하는데, 이 키는 원래 `resetDemoEvent()` 안에서만 심어졌다. 이벤트가 "리셋 버튼을 눌러야" 생기던 예전 구조에선 문제가 안 됐지만, 이제 이벤트가 **첫 방문 시 자동 생성**되면서 이 키를 심는 코드 경로를 거치지 않게 됐다 — `ReconcileProcessor`(1분 주기)가 재계산해 채워주기 전까지 새로 만든 이벤트는 실제 재고가 남아 있어도 **모든 예매가 "재고가 부족합니다"로 실패**했다. `EventsService.create`/`findOrCreateOwnDemoEvent`가 이벤트 생성 시점에 직접 이 키를 심도록 고쳤다.
>
> **§D(한도 보호) 재확인**: 시뮬레이션 상한(`DEMO_SIM_MAX_VU`)은 그대로 유지하되 **쿨다운을 유저별 키**(`demo:sim:cooldown:{userId}`)로 바꿨다 — 전역 쿨다운이면 한 유저의 시뮬레이션 실행이 다른 유저의 실행을 막아버려 격리 취지와 모순된다.

## 맥락 (Context)

최종 산출물은 **공개 URL로 접속 가능한 포트폴리오 데모**다(로드맵 W4, 기획안 §9). 그런데 "그냥 배포"만으로는 두 가지가 성립하지 않는다.

1. **핵심 가치가 눈에 안 보인다.** 이 프로젝트의 무기는 "순간 대량 트래픽 → 초과판매 0 + 실시간 순번"이다. 그런데 방문자가 **혼자** 브라우저에서 예매 버튼을 한 번 누르면, 겉보기엔 평범한 CRUD와 구별되지 않는다. 동시성·대기열·재고 소진이 **재현되지 않으면** 포트폴리오로서 가장 강한 서사가 통째로 안 보인다.

2. **공개 URL이 무료 티어 위에 있다.** DB는 Neon 무료 tier(0010), 백엔드는 무료/저가 VM이다. 공개되면 크롤러·봇·장난 트래픽이 붙고, 특히 아래에서 추가할 **부하 시뮬레이션 버튼**을 아무나 남발하면 무료 한도를 태운다. 즉 **누구나 들어오되, 아무나 자원을 무한정 소모하진 못하게** 해야 한다.

이 ADR은 "공개 데모를 어떻게 **보여줄 만하게** 만들고, 동시에 **한도 안에서 안전하게** 지키는가"를 정한다.

## 결정 (Decision)

데모 모드를 세 축으로 구성한다.

### A. 진입 게이트 (공유 비번 → API 계층에서 검사)

- 방문자는 랜딩에서 **공유 데모 비번**(env `DEMO_GATE_PASSWORD`)을 입력한다. 통과하면 서버가 **단기 데모 토큰**을 발급하고, 이후 모든 API 요청이 이 토큰을 요구한다.
- **게이트는 반드시 API(백엔드) 계층에 둔다.** 프론트(Vercel)에만 비번을 걸면 봇이 프론트를 우회해 VM의 API를 직접 때릴 수 있다. 무료 티어 부하는 **백엔드/DB에서** 발생하므로, 방어선(신뢰 경계, trust boundary)은 API에 있어야 한다. 프론트 게이트 화면은 **UX 보조막**일 뿐 진짜 방어선이 아니다.
- 비번은 **포트폴리오/이력서에 함께 공개**한다(예: "데모 비번 `sunchak`"). 목적은 비밀 유지가 아니라 **크롤러·자동 봇의 원천 차단** + 방문자에게 "여기는 데모"라는 맥락 부여다.

> **게이트 ≠ 로그인.** 이 프로젝트엔 이미 JWT 로그인(user/admin, 0013)이 있다. 게이트는 그것과 **층위가 다른 별개의 막**이다. 로그인은 "예매 주체가 누구인가"를 식별하고, 게이트는 "이 데모에 들어올 자격이 있나"로 **서비스 전체 진입을 차단**한다. 목적·대상이 다르므로 별도 막으로 둔다.

### B. 데모 장치 3종 (핵심 가치를 눈에 보이게)

1. **부하 시뮬레이션 — 서버측 가상 유저.** 방문자가 "가상 유저 N명 투입" 버튼을 누르면, **서버가** N개의 예매 요청을 스스로 생성해 파이프라인(관문 → HELD → 큐 → 확정)에 흘린다. 그러면 대기열이 채워지고 순번이 실시간으로 줄고 재고가 소진되는 과정이 방문자 눈앞에서 재현된다.
2. **실시간 판매 대시보드 — SSE push.** 재고 잔량·HELD/CONFIRMED 카운트·큐 적체를 **SSE(0006)로 실시간 스트리밍**한다. 시뮬레이션이 도는 동안 숫자가 움직이는 이 화면이 데모의 하이라이트다.
3. **데이터 리셋 (아래 C).**

### C. 데이터 리셋 (자동 주기 + 수동 버튼, 둘 다)

재고가 한 번 소진되면 다음 방문자는 "매진"만 본다 → 재현 불가. 그래서 초기화 장치를 **둘 다** 둔다.

- **자동 주기 리셋**: 스케줄러가 일정 주기(env `DEMO_RESET_INTERVAL_MS`, 예: 10분)마다 데모 이벤트의 재고·예매·Redis 카운터를 초기화하고 `open_at`을 재설정한다. → 방문자는 언제 와도 "오픈 예정/판매중"을 본다(**상시성**).
- **수동 리셋 버튼**: 방문자가 지금 즉시 초기화. → 자동 주기를 기다리지 않고 바로 재현(**즉시성**).
- 리셋은 시드 로직을 재사용한다(STATUS에 적힌 seed 미비를 이 작업에서 함께 해소).

### D. 한도 보호 (시뮬 상한 + 쿨다운)

게이트를 통과한 사람도 시뮬 버튼을 남발하면 무료 티어를 태운다. 그래서 **시뮬레이션 버튼에만** 상한을 건다.

- **1회 최대 가상 유저 수** 제한(env `DEMO_SIM_MAX_VU`).
- **재실행 쿨다운**(env `DEMO_SIM_COOLDOWN_MS`) — Redis로 마지막 실행 시각을 기록해 쿨다운 내 재요청을 거부(429). Redis rate limit은 스택에 이미 있는 도구다.

## 고려한 대안 (Alternatives)

| 주제 | 대안 | 채택하지 않은 이유 |
|---|---|---|
| 게이트 위치 | 프론트(Vercel 비번 보호)만 | 봇이 프론트를 우회해 VM API를 직접 호출 가능. 무료 티어 부하는 백엔드에서 나므로 방어선이 뚫린다. → **API 계층 게이트**. |
| 게이트 방식 | 데모 전용 로그인 계정 하나 배포 | 로그인은 "신원 식별"이지 "전체 진입 차단"이 아니다(층위 혼동). 미로그인 공개 엔드포인트(이벤트 목록 등)는 그대로 노출됨. → **별도 진입 게이트**. |
| 봇 억제 | rate limit만(비번 없이) | 크롤러가 계속 두드리며 한도를 갉음. 비번 게이트가 **원천 차단** + 통과자 남발은 상한으로. → **게이트 + 시뮬 상한** 조합. |
| 시뮬 위치 | 방문자 브라우저에서 다중 요청 발사 | 브라우저는 진짜 동시성 재현이 약하고 방문자 회선·기기에 의존해 **비결정적**. 서버측이 결정적이고 무료 티어에서 **통제 가능**. → **서버측 가상 유저**. |
| 리셋 전략 | 자동만 / 수동만 / 방문자별 격리 | 자동만=즉시 재현 불가, 수동만=상시성 없음. ~~방문자별 격리 이벤트는 세션별 데이터 분리 설계라 복잡도 과함(단일 사용처에 오버엔지니어링)~~ → **Superseded(2026-08-07)**: 모든 Redis 키가 이미 `eventId`로 네임스페이스돼 있어 실제로는 "유저마다 `eventId` 하나"만 있으면 되는 문제였다. 위 개정 이력 참고. → **자동+수동 리셋은 그대로 두되, 유저별 격리도 함께 채택**. |

## 근거 (Rationale)

- **신뢰 경계를 백엔드에 둔다**는 게 이 설계의 학습 핵심이다. "방어를 어디에 치느냐"는 백엔드에서 반복해서 나오는 판단이고, "부하가 실제로 발생하는 곳(DB/서버)을 기준으로 방어선을 잡는다"가 정답이다. 프론트 게이트는 편의일 뿐 경계가 아니다.
- **게이트와 로그인의 분리**는 "인증(누구냐) vs 인가·진입(들어올 수 있냐)"의 층위 구분을 명확히 하는 사례다. 하나로 합치면 목적이 흐려지고 공개 엔드포인트에 구멍이 남는다.
- **데모 장치는 서사를 시각화하는 장치**다. W2에서 만든 "초과판매 0", W3의 "실시간 순번"은 숫자·코드로만 있으면 면접관·방문자에게 안 보인다. 시뮬 + 실시간 대시보드가 그 서사를 **눈에 보이는 데모**로 바꾼다 — 포트폴리오 가치와 직결.
- **자동+수동 리셋**은 상충하는 두 요구(항상 켜져 있는 상시 데모 vs 지금 당장 재현)를 각각의 장치로 동시에 만족시킨다. 하나를 고르면 반대쪽을 잃는다.
- **SSE 재사용**: 데모 대시보드의 실시간 스트림은 W3 2.4에서 만들 SSE와 같은 메커니즘이다. 2.4 SSE를 설계할 때 "확정 push"뿐 아니라 "stats 스트림"도 염두에 두면 이 데모 대시보드가 자연스럽게 얹힌다.

## 결과 (Consequences)

**이득**
- 무료 티어를 태우지 않으면서 **누구나 안전하게 접속**하는 공개 데모.
- 동시성·대기열·재고 소진이 방문자 눈앞에서 재현되는 **"보여줄 만한" 데모**.
- seed/리셋 로직 정비(STATUS의 알려진 틈 해소).

**감수할 것**
- **데모 전용 코드 경로**가 운영 로직에 얹힌다(게이트 가드, 시뮬 엔드포인트, 리셋 잡). 실제 프로덕션엔 없을 것들이므로 **데모 전용임을 코드·문서에 명시**하고 격리한다.
- **자동 리셋이 데이터를 주기적으로 날린다** — 데모라 의도된 동작이지만, 방문자가 만든 예매도 함께 사라짐을 UI에 안내한다.
- 게이트·시뮬 상한·리셋 잡의 유지보수 비용.
- **새 env 키 4개**: `DEMO_GATE_PASSWORD`, `DEMO_SIM_MAX_VU`, `DEMO_SIM_COOLDOWN_MS`, `DEMO_RESET_INTERVAL_MS`. `.env.example`에 값 없이 반영(§4), 비밀값(비번)은 Infisical(0011)에.

**후속 작업(구현 시)**
- **구현 시점은 W4**(배포·관측과 함께). 단 **W3 2.4 SSE 설계 때 stats 스트림을 염두**에 둔다(위 근거).
- 게이트 가드 + 데모 토큰 발급, 서버측 시뮬 엔드포인트(+상한·쿨다운), 실시간 stats SSE, 자동 리셋 스케줄러 + 수동 리셋 엔드포인트, 프론트 게이트/데모 컨트롤 화면.
- 세부는 구현 중 조정될 수 있으며, 크게 바뀌면 후속 ADR로 남긴다.
