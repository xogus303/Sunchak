# 0019. 배포 인프라: VM 직접 운영 + 무료 매직 도메인

- 상태: Accepted
- 날짜: 2026-08-18
- 관련: 0010(DB 호스팅 Neon), 0011(시크릿 Infisical), 0013(인증 방식)

## 맥락 (Context)
`01_기술_로드맵.md` Week 4 "배포"를 시작하며 두 가지를 정해야 했다.
1. **배포 인프라**: VM을 직접 운영할지, 완전 관리형 무료 호스팅(Vercel+Render/Railway 등)을 쓸지.
2. **도메인**: 사용자가 배포용 도메인을 소유하고 있지 않고, 비용을 최저로 유지하고 싶어함. 프론트/백엔드가 같은 도메인이 아니어도 무방하다는 확인을 받음.

두 질문은 서로 얽혀 있다 — 인프라 선택에 따라 도메인 없이 HTTPS를 확보하는 방법이 달라진다.

## 결정 (Decision)
- **VM 1대를 직접 운영**한다. 프론트(`apps/web`)·백엔드(`apps/api`)를 Docker로 올리고 Nginx로 리버스 프록시한다.
- **도메인은 구매하지 않고, 무료 매직 도메인(`sslip.io`/`nip.io`류 — IP를 그대로 서브도메인으로 매핑)을 사용**한다. 이 방식으로 `app.<IP>.sslip.io` / `api.<IP>.sslip.io` 형태의 서브도메인을 얻고, Let's Encrypt로 정상적으로 HTTPS 인증서를 발급받을 수 있다. 비용 0원으로 서브도메인 공유(쿠키 `Domain=.<IP>.sslip.io`, `SameSite=Lax` 유지) 구조를 그대로 쓴다.

## 고려한 대안 (Alternatives)
| 대안 | 장점 | 단점 / 채택하지 않은 이유 |
|---|---|---|
| **완전 관리형 무료 호스팅** (Vercel + Render/Railway) | 서버·인증서 관리 불필요, git push로 배포 자동화 | 백엔드 무료 플랜은 유휴 시 슬립 → BullMQ 상시 워커(sweep 30초·admission 2초·reconcile 1분 주기)가 멈춤. 자체 Prometheus를 못 올려 로드맵 4단계(관측)를 재설계해야 함. k6 부하테스트도 무료 플랜 제한에 걸릴 수 있음. 인프라 운영 학습 기회가 사라짐(§0 학습 최우선 원칙과 상충). |
| **도메인 구매 후 서브도메인 공유** | 가장 표준적인 방식 | 이번 요구(비용 최저)와 안 맞음 — 매직 도메인으로 동일 효과를 무료로 얻을 수 있어 불필요한 지출. |
| **프론트/백엔드를 다른 오리진으로 분리 배포** | 리버스 프록시 설정 불필요 | 어차피 양쪽 다 HTTPS가 필요해(mixed content 정책 + 쿠키 `Secure` 요구) 인증서 문제가 사라지지 않음. `SameSite=None`으로 전환해야 해 기존 로컬 개발(`SameSite=Lax`)과의 차이가 커짐. 매직 도메인을 쓰면 이 분리 자체가 불필요. |
| **VM + 매직 도메인 서브도메인 공유 (채택)** | 비용 0원, 로드맵의 관측·부하테스트·상시 워커와 자연스럽게 맞물림, 인프라 학습 가치 확보, 로컬 개발과 동일한 `SameSite=Lax` 쿠키 전략 유지 | Nginx·인증서 갱신·서버 패치를 직접 관리해야 함(단, 이 부담 자체가 이 프로젝트의 학습 목표). |

## 근거 (Rationale)
이 프로젝트는 로드맵에 이미 상시 백그라운드 워커(BullMQ), 자체 관측(Prometheus+Grafana), 부하테스트(k6)가 포함돼 있고 셋 다 "항상 켜져 있는 서버"를 전제로 설계됐다. 매니지드 무료 호스팅은 이 셋과 구조적으로 부딪힌다. 비용 면에서도 VM이 밀리지 않는다(Oracle Cloud Always Free 등 영구 무료 티어 활용 시 인프라 비용 0원 가능, 안 되면 월 $4~6대 저가 VPS로 대체). §0의 "최우선은 학습"에 따라 직접 운영 부담을 학습 기회로 본다. 도메인 미보유·비용 최저 조건은 매직 도메인으로 해소되며, 이 경우 서브도메인 공유가 리버스 프록시 동일 오리진화보다 표준적이라 선택했다.

## 결과 (Consequences)
- **VM 공급자: Oracle Cloud Always Free 확정**(2026-08-18, 사용자 확인). 가입 시 리전별 재고 문제로 즉시 발급이 안 될 경우 Hetzner 등 저가 VPS로 대체.
- Nginx 설정에서 `app.<IP>.sslip.io`(프론트)·`api.<IP>.sslip.io`(백엔드) 두 서버 블록을 구성하고 Let's Encrypt(certbot)로 각각 인증서를 발급한다.
- 쿠키 설정(`common/auth-cookie.ts`)은 기존 `NODE_ENV` 분기를 그대로 사용하되, `Domain` 속성을 `.{IP}.sslip.io`로 지정해야 한다.
- Google OAuth 콜백 URL(`GOOGLE_CALLBACK_URL`)과 `WEB_APP_URL`을 실제 매직 도메인으로 교체해야 한다(Google Cloud Console의 승인된 리디렉션 URI도 함께 갱신).
- IP가 바뀌면(VM 재생성 등) 매직 도메인도 함께 바뀐다 — 향후 실제 도메인을 구매하면 이 ADR을 Superseded로 표시하고 전환한다.

## 개정 이력

- **2026-08-21**: 위 "결정"·"결과" 절에 적힌 "쿠키 `Domain` 속성을 `.{IP}.sslip.io`로 지정해야 한다"는 계획이 틀렸음을 실제 배포 작업 중 발견해 정정한다. `Domain` 속성은 "이 쿠키를 어떤 호스트들에도 같이 보낼지"를 정하는 것인데, 이 프로젝트의 인증 쿠키는 `api.<IP>.sslip.io` 한 곳으로만 오가고(`app.<IP>.sslip.io`는 httpOnly라 읽지도 않고 이 쿠키를 실어 보낼 일도 없음) `Domain`을 안 정해도 기본값(발급 호스트에만 전송)이 이미 원하는 동작이다. 실제로 서브도메인 간 쿠키 전송을 담당하는 건 `common/auth-cookie.ts`에 이미 있던 `sameSite: isProd ? 'none' : 'lax'`이며, 이건 `Domain`과 무관한 별개 메커니즘이다. **코드 변경 없음** — 계획 자체가 오류였다.
